# 法令RAG・LLM調査案件の設計／評価チェックリスト

## 1. 文書の目的

本書は、このリポジトリのGit履歴と設計・評価文書から確認された課題を抽象化し、
他の法令RAG、規制文書検索、LLM調査案件で再利用できるチェックポイントとしてまとめたものである。

法的判断の正しさを本チェックリストだけで保証するものではない。自動評価に加え、
代表的な回答を専門知識のある担当者が確認する。

## 2. 最重要の原則

1. 正答率だけでなく、結論に必要な条文の完全到達率を測る。
2. 検索失敗を一括りにせず、候補生成から最終引用までの脱落地点を記録する。
3. GraphでArticleを発見したことと、その本文を取得・確認したことを区別する。
4. 候補数を増やす前に、候補単位、多様性、コンテキスト、時間予算を確認する。
5. LLMを判断主体にしても、ID検証、証拠境界、時間上限はプログラムで守る。
6. 法令時点差、誤gold、複数正解を検索ロジックで無理に吸収しない。
7. 日本語Analyzer、ID、投入データの完全性をLLMモデル選択より先に確認する。

## 3. データ・索引

- [ ] 評価データと投入法令の基準日を記録している。
- [ ] 法律だけでなく、必要な政令、府省令、告示、ガイド等を投入している。
- [ ] 投入対象外の資料とその理由を記録している。
- [ ] 本則と附則の同じ条番号を別のID名前空間へ分離している。
- [ ] 「第2条の12」「第二号の二」等の枝番を整数化せず保持している。
- [ ] documentId、Article ID、Paragraph ID、Item IDの生成規則が決定的である。
- [ ] OpenSearch、Graph、原文・派生ストレージのIDと件数を照合できる。
- [ ] dangling edgeを自動補完せず、監査または投入エラーとして扱う。
- [ ] schema、mapping、Graph抽出規則を変更した場合に再シードしている。
- [ ] seed後にschema version、node数、edge数、authorityType等を棚卸ししている。
- [ ] PDFの見出し、段落、表、対応表が前処理で失われていない。
- [ ] 原本と派生成果物をSHA-256等で対応付けている。
- [ ] 部分投入時に必要Articleを落としていない。
- [ ] 全文投入時のGraph・検索性能悪化を測っている。

### 今回確認された代表例

- 本則と附則で同じ`article-N`を使い、本則Articleが後勝ちで消えた。
- 枝番を整数化した結果、隣接する条・号とIDが衝突した。
- 民法の必要な28条程度のために全1000条超を投入し、Graphが肥大化した。
- PDFの対応表が単純なテキスト抽出で崩れ、ガイドと条文の関係を利用できなかった。

## 4. 日本語検索

- [ ] OpenSearchの`_analyze`で代表的な法律用語の分割結果を確認している。
- [ ] 日本語が一文字単位に分割されていない。
- [ ] `minimum_should_match`未指定のOR検索で候補が膨張していない。
- [ ] `heading`のboostが本文より過度に強くない。
- [ ] 形態素、phrase、N-gram、vectorを独立レーンとして比較できる。
- [ ] N-gramを追加した場合、query側Analyzerとの組合せを確認している。
- [ ] 「及び／又は」等、法的意味を持つ語をstopwordとして無条件に削除していない。
- [ ] 条番号または確認済みArticle IDは類似度に依存せず直接取得できる。
- [ ] documentId確定後の検索で、法令名を不要にスコアへ混ぜていない。
- [ ] 同じ目的の旧検索APIと新検索APIが並存していない。
- [ ] LLM主導経路とルール主導経路が同じ検索基盤を利用している。
- [ ] Analyzer変更時にvector、filter、keyword等の既存mappingを落としていない。

### 今回確認された代表例

検索語が一文字単位に分割され、`minimum_should_match`未指定、見出しの高boostが重なった結果、
必要な民法622条の2が41候補中25位になった。候補上限だけを増やすとノイズと時間も増えるため、
Analyzerと検索条件の改善が先に必要だった。

## 5. 候補管理・再ランキング

- [ ] 法令はArticle単位、ガイドはchunkまたはpage単位で候補管理している。
- [ ] 長いArticleの複数項・号が候補上限を独占しない。
- [ ] 一つの法令または文書が候補を独占しない。
- [ ] 複数文書・起点Articleをラウンドロビン等で分散して提示する。
- [ ] 候補プール、融合、再ランカー入力、回答コンテキスト、最終引用を分けて記録する。
- [ ] Cross-Encoderを法的な根拠完全性の判定器として扱っていない。
- [ ] 複数論点の質問全文と単一の具体化条文だけを比較して順位を決めていない。
- [ ] Cross-Encoderは同じ論点・役割内のソフトな順位付けとして利用している。
- [ ] 明示条文や高信頼Graph候補を類似度の低さだけで削除していない。
- [ ] 保護枠が全体順位枠を使い切らない上限になっている。
- [ ] chunk単位の枠消費とArticle単位の論点被覆を区別している。
- [ ] 候補上限を再現率、ノイズ率、レイテンシの実測で決めている。

### 必須の失敗地点

traceと評価ログで、少なくとも次の5段階を区別する。

1. 候補プールにない。
2. 候補プールにはあるが、再ランカー入力にない。
3. 再ランカー入力にはあるが、回答コンテキストにない。
4. 回答コンテキストにはあるが、LLMが使用しない。
5. LLMは使用したが、最終引用に残らない。

## 6. 法令構造・Graph

- [ ] 法律、政令、府省令等のauthorityTypeを管理している。
- [ ] 法令レイヤーと、定義・委任・準用・例外・手続等の法的役割を別軸で管理している。
- [ ] edge typeごとに方向、意味、生成元、confidenceを定義している。
- [ ] ドキュメント、コードのedge registry、実Graphの内容を監査できる。
- [ ] 同じ条番号を持つ別法令へ誤接続しないよう法令系統を解決している。
- [ ] LLMが推測した関係だけで確定Graph edgeを作っていない。
- [ ] 未確認RelationAssertionを法的根拠の充足に使っていない。
- [ ] Graph edgeだけで回答せず、接続先Article本文を取得している。
- [ ] Graphで発見した下位法令を回答前に確認すべきか、LLMまたは明示した判定主体が判断する。
- [ ] Graph APIにbatch、hop、件数、timeoutの上限がある。
- [ ] 循環参照と重複展開を防止している。
- [ ] edge抽出規則変更後にGraphを再構築している。

## 7. ガイドライン

- [ ] ガイドを法令本文の代替根拠として扱っていない。
- [ ] ガイドと法令を同一のmandatory根拠枠で競争させていない。
- [ ] 対応表や「法第N条関係」等、機械的に確認できる場合だけ`EXPLAINS`を登録している。
- [ ] 単なる言及である`MENTIONS`を根拠充足に使っていない。
- [ ] ガイドから発見したArticleの本文を別途取得している。
- [ ] 回答と引用で、法令と行政解釈・実務上の取扱いを区別して表示している。
- [ ] 表形式の対応関係を抽出できない場合、推測でGraphを生成していない。

ガイドは法的結論の直接根拠ではなく、自然言語と法令、または法令同士の関係を発見する
「羅針盤」として利用する。

## 8. LLM調査・反復状態

- [ ] プログラムとLLMの責任分担を明示している。
- [ ] プログラムは検索・本文取得・ID検証・予算管理を担う。
- [ ] LLMは法的論点、検索語、追加調査、根拠選択を判断する。
- [ ] 検索、掘り下げ、統合を各サイクルで繰り返せる。
- [ ] 次サイクルへ結論、確定根拠、判断中根拠、未取得Articleを引き継ぐ。
- [ ] 条文IDだけでなく、委任・例外等の関係をDAGとして引き継ぐ。
- [ ] チェックポイント圧縮が不可逆な証拠削除になっていない。
- [ ] 本文や検索履歴を無制限に引き継いでいない。
- [ ] JSON上限へ近づいた場合、説明より根拠ID・未取得Article IDを優先する。
- [ ] 出力JSONを閉じることを説明の詳細さより優先している。
- [ ] 未取得・未知Article IDをコード側で拒否する。
- [ ] 不正な一項目だけで、同じ状態内の検証済み根拠を全て失わない。
- [ ] 統合失敗時に段階判断だけで`ready`へ昇格させない。
- [ ] 中間サイクルのタイムアウトから、検証済みチェックポイントで回復できる。

### `ready`判定

- [ ] `ready`直前に、結論を支える本文が選択済みか確認する。
- [ ] LLM自身が必要と判断して残した未取得Articleを見直す。
- [ ] 残り予算で取得可能なら、本文取得後に採否を判断する。
- [ ] 質問された全事項・全例外の完全調査を終了条件にしない。
- [ ] 取得不能時に探索を無期限に続けない。
- [ ] 中心的結論に影響する不足は`insufficient`または部分回答として明示する。
- [ ] 中心的結論に影響しない不足は留保として利用者へ示す。

## 9. 最終コンテキスト

- [ ] chunk件数だけでなく総文字数・トークン数を測っている。
- [ ] chunk数を増やしたことで各条文が途中切断されていない。
- [ ] 原則と例外等、一体で必要な根拠をconclusionGroupとして扱う。
- [ ] 一部しか収まらないgroupを中途半端に選択していない。
- [ ] 主論点が落ち、周辺論点とガイドだけで枠が埋まる構成を禁止している。
- [ ] `selectedEvidence`が取得済み証拠カタログに存在する。
- [ ] 切り詰め前後のID、chunk数、文字数をtraceへ残している。

## 10. 時間・障害・運用

- [ ] planner、検索、Graph、reranker、統合、回答を個別計測している。
- [ ] component timeoutに最大逐次呼び出し回数を掛けた総予算が成立する。
- [ ] 回答生成用の時間を探索前に予約している。
- [ ] Graphにもquery timeoutを設定している。
- [ ] クライアントtimeoutがサーバwall timeより長い。
- [ ] 出力token上限を増やした場合、LLM timeoutも同時に見直している。
- [ ] timeout、provider quota、根拠不足、内部エラー、形式エラーを区別している。
- [ ] 再試行失敗時に、最初の有効な結果を破棄していない。
- [ ] shadow処理にも独立した時間予算がある。
- [ ] コードや`.env`変更後にDockerイメージを再ビルドしている。
- [ ] schema・Graph変更後に再シードしている。
- [ ] `/health`でモデル、機能フラグ、時間profileを確認できる。
- [ ] feature flag、shadow mode、ロールバック経路がある。

## 11. 評価

- [ ] 正答率、必要条文到達、引用、回答要点を別々に測る。
- [ ] 同じ法令のどれか一条に当たる`any-hit`だけで合格にしていない。
- [ ] 必要Article完全到達率とArticle再現率を測る。
- [ ] マクロ再現率とミクロ再現率を併記する。
- [ ] 候補、融合、再ランク、コンテキスト、引用を段階別に採点する。
- [ ] 正答だが根拠がない「まぐれ正解」を区別する。
- [ ] 回答要点が正しくても、必要条文の引用漏れを別に記録する。
- [ ] gold回答、gold条文、評価用groupを検索・planner・回答LLMへ渡さない。
- [ ] 法令時点差、誤gold、複数正解を別管理する。
- [ ] goldが存在しない問題を引用率の分母へ混ぜない。
- [ ] 「3月／3か月」等の表記差で採点を誤らない。
- [ ] 同じ問題を複数回実行し、LLMと検索の揺らぎを測る。
- [ ] 既知問題だけでなく、未見質問と言い換え質問で評価する。
- [ ] Cross-Encoder、Graph、ガイドの有無をablationで比較する。
- [ ] 自動指標だけで法的な正答を確定せず、代表問題を人が確認する。
- [ ] metricVersionを記録し、指標定義が異なる結果を直接比較しない。

### データセット既知問題の区分

- `temporal_version_mismatch`: 法令時点が異なり、真偽が変わる。
- `suspected_gold_error`: gold条文・正解に誤りの疑いがある。
- `multiple_valid_answers`: 単一正解性に疑義がある。
- `reference_scorable=false`: 評価可能な期待根拠がない。

既知問題は公式集計から消さず、全問集計と診断用集計を分ける。既知問題の情報は評価後に付与し、
検索・再ランキング・回答生成へ渡さない。

## 12. 段階的な導入ゲート

### Phase 0: 基盤確認

- [ ] 投入データ、ID衝突、Graph件数、Analyzer、時間profileを棚卸しした。
- [ ] 旧方式の精度・レイテンシ・timeout率をbaselineとして保存した。
- [ ] 検索、Graph、rerankerの実測スループットを確認した。

### Phase 1: Retrieval-only

- [ ] LLM回答を生成せず、必要Article候補再現率を比較した。
- [ ] どの段階で必要Articleが脱落したか説明できる。
- [ ] 問題・法令・条番号固有の救済ルールを追加していない。

### Phase 2: Shadow

- [ ] 同一入力、同一候補から旧方式と新方式を比較した。
- [ ] shadow未完了・時間切れ行を正常比較へ混ぜていない。
- [ ] 現行回答のレイテンシと成功率を悪化させていない。

### Phase 3: Active少数問

- [ ] 自然言語質問と選択式質問の双方で確認した。
- [ ] 必要Article完全到達率、回答要点、正答率を確認した。
- [ ] timeout、quota、形式エラーを不正解と分離した。

### Phase 4: 全件評価

- [ ] 既知問題を含む公式集計と、除外した診断集計を併記した。
- [ ] 現行で正答していた問題に重大な回帰がない。
- [ ] 未見質問・言い換え質問で過学習を確認した。
- [ ] 代表的な回答を専門知識のある担当者が確認した。

## 13. 最低限のリリース判定

次を満たさない場合は、正答率が高くても法令RAGの改善完了とは扱わない。

1. 必要Article候補再現率がbaseline以上。
2. 必要Article完全到達率がbaseline以上。
3. 主論点の根拠Articleが回答コンテキストに含まれる。
4. Graphだけ、またはガイドだけを直接根拠にした法的結論がない。
5. goldが推論経路へ流入していない。
6. timeout率と全体p90が採用した時間profile内に収まる。
7. timeout、quota、形式エラー、根拠不足をtraceで区別できる。
8. 現行正答問題に重大な回帰がない。
9. 固定問題ルールなしで法律→政令→府省令の必要な接続へ到達できる。
10. 専門知識のある担当者による代表回答レビューを完了している。
